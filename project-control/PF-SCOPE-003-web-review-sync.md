# PF-SCOPE-003 — Web Review/Inventory decisions + cross-surface sync proof
Status: IN_PROGRESS
Owner approval: APPROVED 2026-11-03
Objective: One edit path for Web Review/Inventory decisions that enforces the existing floor/approved-price rules (including bulk actions), labels local-vs-cloud state wherever an item is shown or edited, and proves the mobile→web→mobile round-trip against local Supabase.
Current evidence: `apps/web/src/App.jsx` (Review queues, Inventory table + bulk bar, `InventoryDetail` edit dialog, `PhotoReview`, `AddItemDialog`), `apps/web/src/inventory-repository.js` (local preview), `apps/web/src/supabase-inventory-repository.js` (cloud), `apps/mobile/lib/cloud-inventory-sync.ts` (mobile upsert shape), `scripts/check-live-db.mjs` (PF-SCOPE-001 live-DB harness). Findings before implementation (read from the code, 2026-11-04):
- Only the `InventoryDetail` edit save enforced the floor rule ("Approved listing price cannot be lower than the floor price") and high ≥ low. `AddItemDialog` checked high ≥ low only, never listing price vs floor. `PhotoReview` AI saves wrote low/high/floor/listing price with no validation at all. Bulk actions (`Mark ready`, `Mark Facebook listed`, `Mark eBay listed`) applied status marks with no validation and no per-item failure reporting.
- Local-vs-cloud state was shown only by a topbar badge ("Cloud data" / "Local preview data"). Nothing in Review, Inventory, or the item detail said which dataset was being edited.
- Mobile sync and the web cloud repository upsert the same `inventory_items` table on `(owner_id, client_id)` with the same decision columns, but no live round-trip proof existed.
- The web re-implements pricing/display rules in plain JS instead of using `packages/core` / `packages/api-client` (TypeScript). That duplication is noted and deliberately NOT consolidated in this scope; the shared validator below lives in the web app in its existing plain-JS style.
Included: a shared pure decision validator + bulk-decision helper in the web app, wired into every price-setting web save path (edit dialog, add-item, AI photo-analysis save) and into bulk actions (validate each candidate, skip violators, report counts/reasons, never save a failing item); explicit data-source labelling in the Review view and the item-detail header; a cross-surface round-trip section in the existing live-DB harness (mobile-shape write → web-shape read → web-shape write → mobile-shape read, asserting decision fields and ledger balances survive); `node:test` coverage for the validator/helper following the existing web test layout.
Excluded: new views; pricing-policy changes (the floor/approved-price rules themselves are unchanged — only their enforcement is unified); outbound eBay actions (the eBay publish flow is untouched; bulk "Mark eBay listed" remains a local mark, not a post); AI reactivation; production/hosted database writes; migration edits; RLS/auth changes; mobile capture changes; TestFlight/Apple work; shared-package consolidation.
Preserved UX: same screens, navigation, and workflow copy; the edit dialog keeps its existing validation messages verbatim; bulk buttons keep their labels; the topbar badge text is unchanged. Price-preserving saves (photos, status-only workflow buttons) are not re-validated, so fixing photos or status on a legacy record is never blocked — only price-setting saves and bulk decisions (which assert decision-completeness) are gated.
Dependencies: PF-SCOPE-001 harness + CI (the round-trip section extends `scripts/check-live-db.mjs` without changing its existing assertions); PF-SCOPE-002 is unmerged and this branch does not depend on it (branched from `main` `c6179b35`). Local Supabase cannot run in this VM (no Docker), so the round-trip section is CI-proven only.
Risks and protected operations: none. No hosted writes, no outbound marketplace actions, no credential/auth/RLS changes, no migration edits. The harness runs only against disposable local Supabase and refuses non-loopback hosts.
Acceptance criteria:
- [ ] Observable user result: editing, adding, or AI-saving an item with an approved price below its floor (or high below low) is refused with the existing message and nothing is saved; bulk "Mark ready" applies only to items passing the same rules and reports how many were skipped and why.
- [ ] Error/offline/recovery behavior: a refused save leaves photos, draft values, and existing records untouched; a bulk save that fails partway reports the failure instead of claiming success; local-mode edits are labelled as browser-only before saving.
- [ ] Data/security and regression checks: `npm run check` exit 0; new validator/helper tests pass; CI live-DB run passes including the round-trip section; no migration, RLS, or eBay-behaviour change.
Verification: `npm run check` (includes web `node --test` + `check.mjs` + Vite build); `node --test apps/web/scripts/item-decision-model.test.mjs`; CI check runs on the PR (migration replay + live-DB round-trip); manual browser pass: sign-in/sign-out data-source labels, below-floor refusal in each price-setting path, bulk skip reporting, Review→detail→save→Inventory consistency. VERIFIED requires the CI green run AND the manual browser pass — terminal evidence alone does not close this scope.
