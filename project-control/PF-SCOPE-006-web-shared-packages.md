## Findings (implementation, 2026-11-04) — read before judging acceptance

Build spike VERIFIED: Vite 8 resolves both `@palletscanner/core` and `@palletscanner/api-client` TypeScript sources with no config change (temporary entry import, `vite build` exit 0, tree reverted before implementation).

Migrated (zero behaviour change, equivalence-tested): `getItemPhotos` from core at the three Vite-bundled call sites whose legacy expression is character-identical in semantics — `PhotoReview` in `apps/web/src/App.jsx`, `getEbayListingPayload` in `apps/web/src/web-services.js`, `ItemThumbnail` in `apps/web/src/dashboard-components.jsx` — plus the workspace dependency wiring (`apps/web/package.json`, one-line lockfile sync) and 49 `node:test` equivalence cases in `apps/web/scripts/shared-packages-equivalence.test.mjs` (49/49 pass; `npm run check` exit 0 including `vite build`).

Evaluated, NOT migrated — the proposal's evidence inventory overstated the duplication. Each family below was read in full; replacing it with the core helper would change behaviour or redesign core, both forbidden by this scope. The helpers stay in the web, deliberately, with the reason recorded:
- Field normalization (`price()` in `App.jsx`, `normalizeItem` in `inventory-repository.js`, the Supabase row mapping): no core equivalent exists; the dual `low`/`low_price` tolerance, SKU derivation, and balance defaults are web-specific, and core types are single-field.
- Summaries/metrics (`summarizeInventory`/`summarizePallet` vs core `calculateInventoryTotals`/`calculatePalletMetrics`): different output shapes (web adds `needsFacebook`/`needsEbay`, `unresolved`, `margin`) and different quantity semantics (web `getQuantity` prefers `available`; core uses `quantity`). `apps/web/scripts/check.mjs` pins the web shape.
- Listing drafts/readiness (`createListingDrafts`, `getPostingReadiness`, `getPlatformListingContent`): the web's AI-merge falls back to the existing platform value, core falls back to the general title; web platform content falls back to the item name, core does not; readiness is computed server-side and no web call site exists for `getPostingReadiness`.
- Parsing (`parseMoneyAmount`/`parsePriceRange`/`parsePositiveInteger`/`sanitizeBarcodeValue`): no web call site shares their semantics; `Number()` coercions and the web's uppercasing barcode normalization differ.
- `preferredListingPrice`: a `localStorage` preference rule (low/midpoint/high); no core equivalent.
- Workflow status, work filters, CSV/report builders, ledger balances: different vocabularies, purposes, or inputs (web consumes server-computed balances; no movements-array call site).
- `hasListingPhoto` / `isMissingPlatformListing`: PROVEN behaviour-identical (covered by the equivalence tests) but their call sites live in Node-imported modules (`dashboard-model.js`, `inventory-repository.js`, `supabase-inventory-repository.js`), and core's package entry is not Node-ESM-resolvable — `packages/core/index.ts` re-exports `./src` with extensionless specifiers, which Node 24 rejects (verified: entry import fails, direct `.ts` file import works). Migrating those sites would break `npm run check` under Node. Blocked on a core-side entry-resolution fix, which is a core redesign question and therefore a follow-up scope, not this one.
- `packages/api-client`: evaluated, NOT adopted. No runtime fit for the plain-JavaScript web: `createEbayApiClient` differs from the web's `backendRequest` in base-URL resolution (preferences/origin), auth-token source, and error-message parsing, and the package otherwise exposes only TypeScript types, which have no runtime value in JS. The web keeps `backendRequest`. The gameplan doc's "ready for future web use" phrasing (`docs/web-mobile-split-gameplan.md:236`) was checked and left as aspirational; no doc correction was needed.

Acceptance-criteria deviation (owner decision required): the proposal's criterion "all four rule families migrated, duplicated implementations removed" is NOT met, because meeting it would require changing behaviour or redesigning core. The zero-behaviour-change rule and PF-D-002 (preserve prior work) take precedence.
